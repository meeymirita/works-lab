Наследство: чужая база на Prisma 7

Чужая грязная база «Прокат снаряжения» превращается в типизированный слой данных на Prisma 7 и TypeScript: аудит и db pull, схема и клиент, связи и N+1, пагинация, индексы и EXPLAIN, raw SQL и TypedSQL, миграции на живой базе, внешние ключи и слияние дублей, транзакции и гонки, двойная бронь на диапазонах, деньги и идемпотентность, расширения клиента, мультитенантность и RLS, пул и нагрузка, тесты и CI, итоговое ТЗ.

Стек: Prisma 7, TypeScript, PostgreSQL 18, Node.js 24, Docker, Vitest. Уровень: Средняя–высокая.

Чужая база становится схемой

prisma db pull читает таблицы и пишет по ним модели. Дальше схему приходится причёсывать: давать нормальные имена через @map, превращать числа статусов в enum, заводить связи, которых в базе нет. Версии закреплены явно, а адрес базы лежит в prisma.config.ts.

  • db pull не видит модель без первичного ключа
  • @map и @@map: красивые имена в коде, старые в базе
  • baseline превращает существующую базу в нулевую миграцию

Один вызов — сколько SQL?

Клиент с адаптером pg пишет SQL за вас, и его нужно читать: лог запросов показывает, что реально ушло в базу. Вложенный include в цикле даёт N+1, а relationLoadStrategy join собирает связи одним запросом. На большой выборке OFFSET деградирует, cursor нет.

  • log: ['query'] — смотрим SQL, который шлёт Prisma
  • include и select определяют форму SQL
  • cursor вместо skip на глубоких страницах

Менять схему, пока работает «прод»

Типы колонок меняют по схеме expand/contract: добавить новую колонку, заполнить батчами, переключить код, удалить старую. migrate dev сам создаёт SQL, но переименование превращает в DROP и ADD, поэтому миграцию создают с флагом --create-only и правят руками. Внешние ключи на живой таблице добавляют как NOT VALID.

  • --create-only и ручная правка migration.sql
  • NOT VALID, затем VALIDATE CONSTRAINT без долгой блокировки
  • migrate deploy в CI, migrate dev только локально

Гонки, повторы и двойная бронь

Проверка «свободно ли» перед вставкой не спасает от гонки. Серьёзную защиту даёт база: exclusion-ограничение на диапазоне дат, в схеме Prisma оно описывается как Unsupported, а нарушение приходит ошибкой. Для Serializable ловят P2034 и повторяют транзакцию с паузой.

  • isolationLevel: Serializable и повтор при P2034
  • EXCLUDE USING gist на tstzrange против двойной брони
  • SKIP LOCKED для очереди выдачи без дублей

Soft delete, аудит и изоляция филиалов

client extensions оборачивают каждый запрос: фильтруют удалённые строки, пишут аудит, подставляют филиал. Для RLS филиал передаётся через set_config внутри транзакции, иначе соединение из пула сохранит прежнее значение и один филиал увидит чужие брони.

  • $extends с query, result и model
  • set_config внутри транзакции, а не вне её
  • роль приложения без прав на DDL

Когда Prisma не хватает

Оконные функции, CTE и LATERAL проще писать на SQL. $queryRaw с tagged template передаёт параметры отдельно и защищает от инъекции, а склеивание строк через $queryRawUnsafe открывает дыру. TypedSQL превращает файл .sql в функцию с типизированным результатом.

  • $queryRaw`...${value}` — параметры не склеиваются
  • count возвращает BigInt, деньги — Decimal
  • TypedSQL: .sql файл и prisma generate --sql
