NestJS Lab

DI руками, JWT-ротация, real-time

Helpdesk API собран с нуля слой за слоем: свой мини-DI контейнер, границы модулей и provider scopes, Prisma и транзакции, JWT-ротация refresh-токенов с reuse-detection, RBAC через TicketPolicy, доменные события и WebSocket-шлюз, свой динамический модуль, unit и e2e тесты.

Стек: NestJS 11, Prisma 7, PostgreSQL 18, JWT + argon2, Socket.IO. Уровень: Высокая.

Что на самом деле делает контейнер Nest

Мини-DI-контейнер на 25 строк собирает граф зависимостей по метаданным конструктора. После этого @Injectable и токены перестают быть магией; ловушка — забытый декоратор, из-за которого класс не резолвится.

  • reflect-metadata и design:paramtypes
  • Синглтон по умолчанию: один экземпляр на всех
  • Понятная ошибка с путём зависимостей

Prisma: обновление и история атомарно

Обновление тикета и запись истории изменений выполняются в одной транзакции. Если запись истории упадёт, изменения тикета тоже откатятся.

  • $transaction с интерактивным tx
  • diff до/после по отслеживаемым полям
  • Счётчик version для оптимистичных проверок

Refresh-токены и reuse-detection

Каждый refresh-токен одноразовый: при обновлении старый отзывается и выдаётся новый в той же «семье». Повторное предъявление отозванного токена считается кражей и гасит всю семью.

  • В БД хранится хэш, а не сам токен
  • compare-and-set против гонки двух запросов
  • revokeFamily при обнаружении повтора

RBAC и TicketPolicy

Роль проверяется guard'ом через метаданные, а права на конкретный тикет — отдельным классом-политикой. Guard не видит тело запроса, поэтому проверки по DTO живут в сервисном слое.

  • SetMetadata и Reflector.getAllAndOverride
  • scopeFor: условие видимости в каждом запросе
  • Разрешённые переходы статусов

Сервис не знает про сокеты

Сервис тикетов публикует типизированные события, а слушатели решают, что с ними делать: слать в WebSocket, писать аудит. Связность падает, добавить реакцию можно без правки сервиса.

  • @nestjs/event-emitter и wildcard-имена
  • Классы событий вместо строк с данными
  • EventEmitter в процессе против брокера

Real-time с проверкой прав

Шлюз проверяет JWT один раз при подключении, раскладывает сокеты по комнатам и повторно проверяет доступ при подписке на тикет. Комнаты не переживают перезапуск сервера, поэтому клиент подписывается заново.

  • Токен в handshake.auth, а не в query
  • Комнаты user:, ticket:, agents
  • Подписка через ту же TicketPolicy
